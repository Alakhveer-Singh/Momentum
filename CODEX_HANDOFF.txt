PROJECT OVERVIEW
================================================================================

Project Name:
  Quibus LMS (Lead Management & CRM System)

Primary Objective:
  Build a production-ready lead management and CRM system enabling sales teams
  to track prospects through a multi-stage pipeline, manage activities, score
  leads, and generate analytics.

Business Purpose:
  Replace manual spreadsheet-based lead tracking with real-time kanban pipeline
  visualization, automated scoring, bulk communication, and team performance
  analytics.

End Users:
  - Sales Representatives: manage leads, log activities, send emails
  - Sales Managers: view team performance, generate reports, assign leads
  - Administrators: manage users, templates, system configuration

Current Development Stage:
  BETA - All core features complete, UI refactored to professional icons
  (lucide-react, no emoji), both Laravel and Django backends implemented.
  Ready for production deployment after final verification.


SYSTEM ARCHITECTURE
================================================================================

High-Level Architecture:
  Three-tier stack: React 19 frontend (Vite + Tailwind) → Django 6 backend
  (DRF + Channels) → MariaDB/MySQL database.

  Client layer communicates via REST API (/api/* routes) + WebSocket
  (ws://localhost:8000/ws/crm). JWT tokens authenticate both REST and
  WebSocket connections. Real-time updates broadcast via Django Channels.

Components:

  FRONTEND (React 19):
    - Pages: Login, Dashboard, Leads, Pipeline, Tasks, Templates, Reports, Users
    - Sidebar navigation with professional lucide icons
    - Layout.jsx: master layout with header, sidebar, notifications
    - AuthContext: JWT token management, user state, WebSocket auto-connect
    - API client: Axios instance with Bearer token injection
    - WebSocket client: echo.js (native WebSocket, not Laravel Echo)

  BACKEND (Django 6):
    - DRF ViewSets: LeadViewSet, ActivityViewSet, TaskViewSet, etc.
    - Channels Consumer: crm_consumer.py authenticates JWT, broadcasts updates
    - Models: User (with role enum), Lead (soft-delete, scoring), Activity,
      Task, EmailTemplate, CustomFieldDefinition, Notification, PipelineStage
    - Scoring service: Lead.score (0-100) from source quality, stage,
      engagement, profile completeness
    - Permissions: Role-based (admin, manager, rep)

  DATABASE (MariaDB):
    - ~10 tables: users, leads, activities, tasks, email_templates,
      custom_field_definitions, notifications, pipeline_stages,
      custom_field_values (JSON store), audit_logs
    - Soft-delete pattern: deleted_at nullable timestamp
    - Indexed on: stage_id, owner_id, source, status, created_at

Services:
  - Django built-in ORM (no additional ORM needed)
  - DRF serializers for JSON responses
  - Channels ASGI for WebSocket
  - ReportLab for PDF exports
  - PyMySQL for MySQL/MariaDB connection (pure Python, no C deps)

APIs:
  - REST: POST /api/auth/login, GET /api/leads, PUT /api/leads/{id},
    POST /api/activities, GET /api/reports/*, POST /api/exports/*
  - WebSocket: ws://localhost:8000/ws/crm?token=JWT_TOKEN
    Events: lead.updated, notification (broadcast to connected clients)

Data Flow:
  User login → JWT token issued → Token stored in React state + localStorage
  → All REST requests include "Authorization: Bearer {token}"
  → WebSocket connects with ?token=JWT in query string
  → Lead update → Backend broadcasts via Channels → Client receives
    via WebSocket → Dashboard/Pipeline auto-refresh via custom event listener

Technology Stack:

  FRONTEND:
    - React 19, Vite (bundler), React Router 7
    - Tailwind CSS 4 (utility-first styling)
    - lucide-react (line icons, professional appearance)
    - Axios (HTTP client)
    - Native WebSocket (no Socket.io, no Socket.py)

  BACKEND:
    - Django 6.0 (Python web framework)
    - Django REST Framework 3.14+ (DRF)
    - Django Channels 4 (WebSocket support)
    - Daphne 4 (ASGI server for Channels)
    - djangorestframework-simplejwt 5.5 (JWT auth)
    - PyMySQL (pure-Python MySQL driver, no mysqlclient C deps)
    - ReportLab (PDF generation)
    - django-cors-headers (CORS support)

  DATABASE:
    - MariaDB 10.5+ or MySQL 8.0+
    - PyMySQL driver (installed via requirements.txt)

  RUNTIME:
    - Python 3.10+
    - Node.js 18+
    - PHP 8.5+ (not used in current Django backend)

Dependencies:
  - Frontend: package.json pins React 19, Tailwind 4, lucide-react
  - Backend: requirements.txt pins Django 6, DRF, Channels, SimpleJWT
  - Database: MariaDB running on localhost:3306
  - Services: Django Daphne (ASGI), Vite dev server (port 3000)

  Implementation Details:
    Six fixed stages: New, Contacted, Qualified, Negotiating, Won, Lost
    Each stage: id, name, position (0-5), color (hex code for UI)

    Drag-drop flow:
      1. User drags lead to new stage (Pipeline.jsx line 30)
      2. Optimistic update: setLeads() updates local state immediately
      3. API call: PUT /api/leads/{id} { stage_id: X }
      4. Backend: Lead.stage_id updated, score recalculated, broadcast sent
      5. WebSocket: Channels consumer sends lead.updated event
      6. Frontend: echo.js listener calls window.dispatchEvent(lead-updated)
      7. Pipeline.jsx useEffect reloads all leads via GET /api/leads?all=1

    Backend scoring on stage change (views.py ~line 160):
      from crm.scoring import calculate_lead_score
      score = calculate_lead_score(lead)
      lead.score = score
      lead.save()

  Known Limitations:
    - No stage creation UI (hardcoded six stages)
    - No permission check (rep can move any lead, should be own only)
    - No undo if drag fails silently

FEATURE 9: WebSocket Real-Time Updates
  Purpose:
    Broadcast lead changes to all connected clients, auto-refresh dashboard

  Files:
    - backend-django/crm/consumers.py: WebSocket consumer
    - backend-django/crm/routing.py: WebSocket URL routing
    - frontend/src/echo.js: Native WebSocket client
    - frontend/src/context/AuthContext.jsx: Auto-connect on login
    - frontend/src/pages/Dashboard.jsx: Event listener

  Implementation Details:
    WebSocket URL: ws://localhost:8000/ws/crm?token=JWT_TOKEN

    Consumer flow (consumers.py):
      1. connect(): extract token from query string, validate JWT
      2. If valid: join groups "leads" and f"user.{user_id}"
      3. accept() or close()
      4. receive(): handle incoming messages (not used currently)
      5. disconnect(): leave groups

    Broadcasting on lead update (views.py ~line 170):
      async_to_sync(channel_layer.group_send)(
        "leads",
        {
          "type": "lead_updated",
          "lead_id": lead.id,
          "event": "lead.updated",
          "lead": serialized_lead_data
        }
      )

    Consumer receives broadcast:
      def lead_updated(self, event):
        self.send(json.dumps({
          "event": event["event"],
          "lead": event["lead"]
        }))

    Client-side (echo.js):
      WebSocket wrapper with event emitter API
      ws.on('lead.updated', callback)
      Auto-reconnect on disconnect with exponential backoff (1s, 2s, 4s, 8s)
      Heartbeat: none (relies on browser/server TCP keepalive)

    Dashboard listener (Dashboard.jsx ~line 40):
      useEffect(() => {
        window.addEventListener('lead-updated', load)
        return () => removeEventListener(...)
      }, [])

  Known Limitations:
    - No heartbeat / ping-pong (relies on TCP)
    - No message queueing if client reconnects (missed updates)
    - No acknowledgment / delivery confirmation
    - No per-user notifications (broadcasts to all)
    - Daphne single-process only (doesn't scale horizontally without Redis)

TECHNICAL DECISIONS
================================================================================

DECISION 1: Django over Laravel for Backend
  Chosen: Django 6 + DRF
  Why: Python ecosystem, Channels for WebSocket (no Reverb complexity),
       pure-Python PyMySQL driver (no C compilation)
  Alternatives: Laravel 13 + Reverb (requires Supervisor, more moving parts)
  Tradeoffs: Django steeper learning curve, but more scalable, standard patterns

DECISION 2: Native WebSocket over Socket.io
  Chosen: Native WebSocket in frontend, Channels consumer in backend
  Why: Simpler protocol, no Socket.io client overhead, direct broadcast
  Alternatives: Socket.io (more feature-rich, cross-protocol fallbacks)
  Tradeoffs: Native WS doesn't auto-reconnect (implemented manually), no fallback

DECISION 3: Lucide Icons over Emoji
  Chosen: lucide-react professional line icons
  Why: Scalable (vector), accessible (screen readers), professional appearance
  Alternatives: Emoji, FontAwesome, Material Icons
  Tradeoffs: Adds dependency, requires icon library consistent sizing

DECISION 4: Soft Delete Pattern
  Chosen: deleted_at nullable timestamp on Lead, Activity, etc.
  Why: Preserve audit trail, allow recovery, no data loss
  Alternatives: Hard delete, flag column (is_deleted), separate archive table
  Tradeoffs: Requires .exclude(deleted_at__isnull=False) in all queries

DECISION 5: JWT Only (No Refresh Tokens)
  Chosen: 60-minute JWT lifetime, must re-login after expiry
  Why: Simpler implementation, no token rotation complexity
  Alternatives: JWT + refresh token, session-based auth
  Tradeoffs: Poor UX if token expires during use, no background refresh

DECISION 6: LaravelStylePagination
  Chosen: From/to/total/per_page response format
  Why: Familiar to Laravel devs, client shows "1-10 of 100"
  Alternatives: Cursor-based, offset-limit, page number only
  Tradeoffs: Frontend expects this format, doesn't scale well for large offsets

DECISION 7: Lead Scoring Formula (0-100)
  Chosen: Source (10-40) + Stage (0-30) + Engagement (5-20) + Completeness (5-10)
  Why: Balanced weighting, all factors considered
  Alternatives: Machine learning model, equal weights, custom formula builder
  Tradeoffs: Static formula, no learning from outcomes, must tune weights manually

DECISION 8: Kanban Stages (Fixed Six)
  Chosen: New, Contacted, Qualified, Negotiating, Won, Lost (hardcoded)
  Why: Standard sales pipeline, simplifies workflow logic
  Alternatives: Custom stages per workspace, dynamic stage creation
  Tradeoffs: Not flexible if team uses different pipeline, stage order fixed

RISKS AND WARNINGS
================================================================================

FRAGILE AREAS (High Risk):

  1. WebSocket Connection on JWT Expiry
     Risk: Socket stays open after token expires, broadcasts fail silently
     Mitigation: Monitor WebSocket errors in production, add heartbeat check
     Avoid: Don't extend JWT lifetime beyond business needs

  2. Lead Score Recalculation
     Risk: If scoring.py algorithm changes, historical scores don't update
     Mitigation: Migration script to re-score all leads if needed
     Avoid: Don't change weights without testing impact

  3. Soft Delete Pattern
     Risk: Queries must .exclude(deleted_at__isnull=False) or data leaks back
     Mitigation: Use manager method Lead.objects.active() everywhere
     Avoid: Direct Lead.objects.all() queries (bypass soft-delete)

  4. Database Connection (PyMySQL)
     Risk: Pure-Python driver slower than mysqlclient, no connection pooling
     Mitigation: Use max_connections in Django settings, monitor pool exhaustion
     Avoid: Opening/closing connections in loops

  5. Single-Process Daphne
     Risk: Channels doesn't scale to multiple servers (no Redis layer)
     Mitigation: Add django-redis + RedisChannelLayer for production
     Avoid: Horizontal scaling without Redis setup

TECHNICAL DEBT:

  1. No refresh token (users logged out after 60 min)
     Effort to fix: 2 hours (add refresh token endpoint, rotate on use)
     Impact if not fixed: poor UX, users must re-login

  2. No permission middleware on views
     Effort to fix: 1 hour (add @permission_required or mixin)
     Impact: rep can see manager-only endpoints (API returns data, but should 403)

  3. No input validation on custom_fields JSON
     Effort to fix: 2 hours (add JSONSchema validation)
     Impact: broken JSON crashes API, no safeguard

  4. No database transaction rollback on bulk operations
     Effort to fix: 3 hours (wrap in transaction, rollback on error)
     Impact: partial bulk send succeeds (inconsistent state)

  5. No test suite
     Effort to fix: 10 hours (pytest + coverage to 80%)
     Impact: regressions go undetected, risky refactors

ASSUMPTIONS SAFE TO MAKE:

  - Database is always up (system assumes connectivity, no failover)
  - Network is always available (no offline support, requires internet)
  - User roles don't change mid-session (no role-refresh logic)
